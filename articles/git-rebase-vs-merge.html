Git rebaseとmergeの違いを完全理解する

概要：どちらもブランチを統合する手段

Gitでブランチを統合する方法は、大きく分けてmergeとrebaseの2つがあります。どちらも最終的には「別のブランチの変更を現在のブランチに取り込む」という目的は同じですが、履歴の形が大きく異なります。

mergeの仕組み

git mergeは、2つのブランチの変更を統合して、新しい「マージコミット」を作成します。履歴は分岐と統合の形を保ちます。

# mainブランチにfeatureを取り込む
git checkout main
git merge feature

# 履歴のイメージ:
# * merge commit
# |\
# | * feature-3
# | * feature-2
# | * feature-1
# * main-2
# * main-1

mergeの特徴：

  • ✅ 履歴がそのまま残る（いつ分岐したか、いつ統合したかがわかる）
  • ✅ 安全（既存のコミットを変更しない）
  • ❌ マージコミットが増えると履歴が複雑になる

rebaseの仕組み

git rebaseは、ブランチの「基底」を別のコミットに移動させます。 feature ブランチのコミットを、まるで main ブランチの最新から分岐したかのように並べ直します。

# featureブランチをmainに追従させる
git checkout feature
git rebase main

# 履歴のイメージ:
# * feature-3 (rebased)
# * feature-2 (rebased)
# * feature-1 (rebased)
# * main-2
# * main-1

rebaseの特徴：

  • ✅ 履歴が直線的で見やすい
  • ✅ マージコミットが不要
  • ❌ コミットハッシュが変わる（履歴を書き換える）
  • ❌ 既にpush済みのブランチに使うと危険

比較まとめ

項目mergerebase
履歴の形分岐・統合直線
マージコミット作成する作成しない
安全性高い共有ブランチでは危険
履歴の書き換えしないする
コンフリクト解決1回コミットごとに発生

いつどちらを使うべきか

一般的なガイドライン：

  • merge → 共有ブランチ（main, develop）に取り込むとき。安全で履歴が保持される。
  • rebase → 自分のfeatureブランチを最新mainに追従させるとき。履歴がきれいになる。
  • 黄金ルール：公開済み（push済み）のブランチにはrebaseしない。
「rebase は自分のブランチで、merge は共有ブランチで」と覚えておけば、まず間違いありません。

コンフリクトの解決

merge でも rebase でも、同じファイルの同じ行を異なる変更をした場合、コンフリクトが発生します。

# merge のコンフリクト
git merge feature
# CONFLICT (content): Merge conflict in index.html

# コンフリクトを解決後
git add index.html
git commit  # マージコミットを完成

# rebase のコンフリクト
git rebase main
# CONFLICT: rebasing

# コンフリクトを解決後
git add index.html
git rebase --continue  # 次のコミットへ

# 中止したい場合
git rebase --abort

rebaseでは、コンフリクトをコミットごとに解決する必要があるため、コンフリクトが多い場合は merge の方が楽になることがあります。

チーム開発でのベストプラクティス

  1. feature ブランチを最新に保つ：作業開始前やPR作成前に git rebase main で最新mainに追従させる
  2. PRはマージコミットで：Squash and Merge または通常のMergeで履歴を明確に保つ
  3. 小さく頻繁に：大きな変更を長期間のブランチで行うと、コンフリクトが大きくなる
  4. コンミットメッセージを整える：git rebase -i でコミットを整理してからPRを出す
# インタラクティブrebaseでコミットを整理
git rebase -i HEAD~3
# pick, squash, reword, fixup でコミットを編集
